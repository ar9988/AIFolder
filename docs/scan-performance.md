# 스캔 성능 개선 기록

SD 카드 전체 스캔이 너무 오래 걸린다는 문제에서 출발해, 계측 → 원인 규명 → 최적화 →
검증을 거친 기록이다. 결론뿐 아니라 **틀렸던 가설과 그걸 어떻게 걸러냈는지**를 같이 남긴다.
다음에 같은 함정에 빠지지 않기 위해서다.

- 대상 기기: LG (Android, 8코어), exFAT SD 카드
- 데이터: 디렉터리 2,884개 / 파일 144,909개
- 측정 빌드: release (minify 적용), `scanProfiling=true`

---

## 1. 목적

1. SD 카드 첫 스캔 시간을 줄인다.
2. 앱에서 만든 파일이 즉시 목록에 뜨지 않는 문제를 고친다.
3. 병렬도(`scanParallelism`)의 적정값을 실측으로 정한다.

---

## 2. 결과 요약

같은 조건끼리 비교한 값이다. 조건 구분은 4장 참고.

| 조건 | 개선 전 | 개선 후 | 변화 |
|---|---|---|---|
| 첫 스캔 · 캐시 재가열됨 | 87.4s | **45.0s** | **-49%** |
| 첫 스캔 · 캐시 차가움 | 146.4s | **81.2s** | **-45%** |
| 재스캔 | 143s | **1.5s** | **-99%** |

개선 후 남은 81초의 내역 (캐시 차가움 기준):

| 구간 | 시간 | 비중 |
|---|---|---|
| 파일 메타데이터 읽기 (병렬 구간 벽시계) | 52.8s | 65% |
| DB 일괄 쓰기 | 14.2s | 17% |
| 목록 읽기 대기 | 6.5s | 8% |
| 제외 규칙 필터 | 1.8s | 2% |

82%가 저장장치 대기다. 코드로 더 짜낼 여지는 크지 않다.

---

## 3. 무엇을 고쳤나

### 3.1 디렉터리 mtime 스킵 — 재스캔 143s → 4.2s

폴더의 mtime은 그 안에서 항목이 생기거나 사라질 때 갱신된다. 저장해둔 값과 같으면
그 폴더의 직속 목록도 그대로이므로, 수십 ms짜리 `readdir` 대신 `stat` 한 번으로 넘어간다.
재스캔에서 99%의 폴더를 건너뛴다.

**한계**: 파일 *내용*만 바뀐 경우는 폴더 mtime이 안 변해서 지나친다. 그래서 사용자가
직접 요청한 스캔(당겨서 새로고침)은 이 경로를 타지 않는다.

**주의**: 저장할 때와 반드시 같은 API로 읽어야 한다. `File.lastModified()`는 초 단위이고
`Files.readAttributes()`는 나노초를 포함해 ms로 환산하므로, 둘을 섞으면 소수점 이하 초가
있는 폴더는 영영 일치하지 않아 매번 다시 읽게 된다.

### 3.2 중복 정규화 · 중복 syscall 제거 — 9.1s

같은 경로를 파일당 세 번 NFC 정규화하고 있었다. 파일 14만 개면 43만 번이고,
`absolutePath` 문자열 생성도 그만큼 따라붙었다. 한 번만 계산해서 뒤 단계로 넘긴다.

| 항목 | 이전 | 이후 |
|---|---|---|
| 제외 규칙 필터 | 7.7s | **1.6s** (-78%) |
| 파일 처리 (스레드 합계) | 11.0s | **7.9s** (-25%) |

같이 제거한 것:

- `detectDirectoryRename`이 이미 읽어둔 `isDirectory` / `lastModified`를 다시 `stat`으로
  물어보고 있었다. 첫 스캔은 조기 반환이 없어 전체 파일 수만큼 그대로 나갔다.
- 숨김 파일 판정의 `Regex`가 호출마다 컴파일되고 있었다. 그 정규식은 첫 글자로 `.`을
  요구하므로 바로 다음 줄의 `startsWith(".")`에 반드시 걸린다 — 논리적 중복이라 삭제했다.

### 3.3 디렉터리 목록 미리읽기 — 가장 큰 몫

기존 구조는 폴더 하나를 완전히 끝내고 다음으로 갔다.

```
listFiles → 필터 → DB읽기 → 파일처리 → DB쓰기 → 다음 폴더
```

`listFiles`가 전체의 62~77%인데, 그동안 DB(내부 저장소)는 놀고 있었다. 자원이 겹치지
않는데 순서 때문에 서로 기다린 것이다.

그래서 **큐에 쌓인 다음 폴더들의 목록을 앞질러 읽는다.** 상태를 만지는 코드는 전부 단일
스레드로 남기므로 동시성 위험이 거의 없다.

```kotlin
for (upcoming in queue) {
    if (readAhead.size >= READ_AHEAD) break
    readAhead.getOrPut(upcoming.file.path) { async { readDirectory(upcoming, fullRescan) } }
}
val directoryRead = (readAhead.remove(directory.path) ?: async { ... }).await()
```

효과는 새로 넣은 `LIST_WAIT`(본체가 실제로 기다린 시간)에 드러난다.

```
디렉터리 나열(스레드 합계)  257,031ms   ← 나열 작업 자체의 양
└ 그중 기다린 시간            6,455ms   ← 임계 경로에 남은 것
```

**함정 하나**: mtime 판정을 본체에 두고 목록만 미리 읽으면, 재스캔에서 건너뛸 폴더까지
전부 읽어버려 3.1의 최적화가 통째로 사라진다. 그래서 **판정을 미리읽기 안에 넣었다.**
미리읽기 작업이 `Unchanged`를 반환하면 목록을 아예 읽지 않는다.

### 3.4 그 밖에

- 앱에서 만든 파일이 즉시 표시되도록 `createResource`가 DB 행을 직접 삽입한다.
  전에는 100초 넘게 걸리는 전체 스캔 뒤에 줄을 섰다.
- `copyResource`가 insert id를 버려서 복사한 폴더의 하위 항목이 `parentId = 0`으로
  들어가 보이지 않던 문제를 고쳤다. (기존 버그)
- `toResource()`에 NFC 정규화가 빠져 있어 한글 파일명이 다음 스캔에서 중복 행을
  만들던 문제를 고쳤다.

## 4. 측정 방법론 — 이쪽이 더 어려웠다

최적화 자체보다 **믿을 수 있는 숫자를 얻는 게** 훨씬 오래 걸렸다. 교란 변수를 발견한 순서대로 적는다.

### 4.1 디버그 빌드로 재면 안 된다

LeakCanary가 강제 GC를 돌리고 ART 최적화도 일부 꺼져 있어, 할당이 많은 스캔은 시간이
크게 부풀려진다. 반드시 release로 잰다.

### 4.2 앱만 지우면 OS 페이지 캐시가 안 지워진다

앱 삭제 후 재설치로 DB를 비우고 6회 연속 측정했더니 이렇게 나왔다.

| 회차 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 전체 | 164s | 92s | 51s | 47s | 41s | 39s |
| 나열 μs/dir | 43,674 | 18,992 | 4,092 | 2,840 | 2,670 | 2,746 |

**병렬도가 아니라 회차 순서를 잰 것이다.** 커널이 들고 있는 SD 카드 dentry/inode 캐시는
앱 삭제로 지워지지 않는다. **매 회차 `adb reboot`이 필요하다.**

### 4.3 재부팅해도 조건이 같지 않다 — 진짜 변수는 dentry 캐시 온도

재부팅을 넣은 뒤에도 결과가 두 무리로 갈렸다. **15회 전부 재부팅했는데도** 그랬다.

```
84.7  84.9  86.0  87.4  87.5  88.1  89.1  89.2  90.0     ← 9회
135.0  135.4  136.0  137.3  157.1  177.5                  ← 6회
```

중간값이 없다. 여기서 두 번 틀린 가설을 세웠다.

| 가설 | 결과 |
|---|---|
| "부팅 후 CPU 부하(loadavg)가 높으면 느리다" | **반증.** 부하가 가장 낮은 회차가 가장 느렸다 |
| "이봉분포다" | **반증.** 표본을 늘리니 14k~48k의 연속 분포였다 |
| "더 오래 기다리면 나아진다" | **반증.** 600초 대기가 180초보다 오히려 나빴다 |

`/proc/meminfo`의 **`SReclaimable`**(dentry/inode 캐시가 들어 있는 슬랩)을 찍자 답이 나왔다.

| 스캔 시작 시점 `SReclaimable` | 결과 |
|---|---|
| ~115 MB | 81~128s (캐시 차가움) |
| ~300 MB | 45~86s (캐시 재가열됨) |

관측 14회 전부 일치했고 겹치는 구간이 없었다. 메커니즘은 이렇다 —
**재부팅은 캐시를 확실히 비운다**(부팅 직후 `SReclaimable`은 6회 모두 86~88MB로 일정).
그런데 그 뒤 앱을 띄우기까지 기다리는 동안 **부팅 후 미디어 스캔이 SD 카드를 훑으면서
캐시를 다시 채운다.** 그게 끝나 있으면 빠르고, 아직이면 느리다.

계측으로도 확인된다. 느린 회차는 CPU를 더 쓰는 게 아니라 기다린다.

| 지표 | 빠른 회차 | 느린 회차 | 배수 |
|---|---|---|---|
| 전체 | 75.8s | 107.6s | 1.42x |
| **앱 CPU 시간** | 42.8s | 45.5s | **1.06x** |
| **iowait** | 17.2s | 68.7s | **3.98x** |
| 빅코어 주파수 | 1,457MHz | 1,800MHz | 1.24x |

벽시계가 1.42배 늘어나는 동안 앱 CPU는 그대로다. 주파수는 오히려 더 높다.

### 4.4 그래서 채택한 프로토콜

```
앱 삭제 → 설치 → 재부팅 → 대기 → SReclaimable 확인 → 150MB 미만이면 측정, 아니면 버리고 재시도
```

이 게이트를 적용하자 채택된 회차의 `SReclaimable`이 110,288~111,976KB(폭 1.7MB)로
모였고, **회차 편차가 13초에서 1.5초로 줄었다.**

수율은 22회 시도에 6회 채택으로 낮다. 대기 180초 동안 캐시가 데워지기 때문이므로,
다시 잰다면 **대기를 60~90초로 줄이는 편이 낫다.**

## 5. 병렬도 결론

### 5.1 `scanParallelism` — 4로 둔다. 4~12는 차이 없다

콜드 게이트를 적용한 6회:

| p | 회차 | 평균 |
|---|---|---|
| 4 | 83.0s, 81.9s | 82.4s |
| 8 | 80.5s, 80.2s | 80.4s |
| 12 | 80.3s, 81.8s | 81.0s |

그룹 간 격차(2.0초)가 그룹 내 편차(1.5초)와 비슷하다. **구분됐다고 말할 수 없다.**

다만 **4 미만으로 내리면 안 된다.** 아래 5.2의 포화점이 4이기 때문이다.

### 5.2 `readdir`은 병렬화되지만 1.4배에서 포화한다

DB에서 디렉터리 경로만 읽어와(파일시스템을 건드리지 않아 캐시가 안 데워진다)
겹치지 않는 그룹으로 나눠 병렬도별로 측정했다. 콜드 2회, 소수점까지 재현됐다.

| 병렬도 | 1 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|
| 순차 대비 | 1.00 | **1.40** | 1.36 | 1.29 | 1.35 | 1.49 |

4에서 포화하고 64까지 안 오른다. 흔들림은 그룹별 항목 수 차이(±15%)로 설명된다.
SD 카드가 FUSE로 마운트돼 있어(`/dev/fuse ... 9C33-6BBD fuse`) 커널 ↔ 유저공간
왕복이 끼는데, 그 경로가 이 이상은 겹쳐주지 않는다.

**그래서 순회 전체를 병렬화하지 않았다.** 1.4배를 얻자고 큐·캐시·버퍼를 전부 동시성
안전하게 만드는 건 수지가 안 맞는다. 미리읽기(3.3)로 같은 이득을 훨씬 낮은 위험에
가져왔다. 실제 이득도 1.4배 자체보다 **DB 쓰기와 겹친 것**이 컸다.

## 6. 계측 도구

| 파일 | 역할 |
|---|---|
| `data/.../scanner/ScanProfiler.kt` | 구간별 누적 시간. 할당을 하지 않아 결과를 거의 왜곡하지 않는다 |
| `domain/.../model/ScanProfile.kt` | 보고서 서식 |
| `gradle.properties` `scanProfiling` | 켜면 logcat에 프로파일 출력 + 반복 측정을 위해 스캔 쿨다운 해제 |

`scanProfiling`은 **배포 빌드에서 반드시 `false`여야 한다.** 상수라서 꺼져 있으면
R8이 로그 호출 자체를 지운다. 디버그 빌드에서는 항상 켜져 있다.

측정 시:

```bash
./gradlew :app:assembleRelease -PscanProfiling=true -PscanParallelism=8
```

## 7. 남은 것

- **파일 메타데이터 읽기가 52.8초(65%)로 새 병목이다.** 다만 `scanParallelism`을
  올려도 안 줄어드는 것으로 보아 SD 카드 포화로 보인다.
- 미리읽기와 파일 `stat`이 같은 디스패처(`limitedParallelism(4)`)를 공유한다.
  분리해서 각각 조절하는 안은 재보지 않았다.
- `READ_AHEAD = 8`을 키워 얻을 수 있는 건 목록 대기 6.5초뿐이라 튜닝하지 않기로 했다.
